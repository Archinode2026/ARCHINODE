# 구현계약서 — 어드민을 「운영 콘솔」로 (단번 관리자 화면 수준)

- **낸 사람**: 노드-골드 (설계 전용 — 코드는 한 줄도 안 고쳤다)
- **받는 사람**: 지휘 창 (이 문서를 단계별 작업지시서로 쪼갠다)
- **근거**: 한울님 2026-09-12 지시 "어드민을 단번 수준으로 만들기"
- **읽은 것**: 루트 CLAUDE.md · 규정집 제1판 · 작업일지 · firestore-schema · firestore.rules · admin/ 6개 파일 · brand-portal/dashboard.html · brands/view.html · products/view.html · list-your-brand.html · 단번 admin.html 메뉴 구조(1530~1600줄) · 엑사 「전 화면 공통 장치」 설계노트
- **못 본 것**: 7절

---

## 1. 배경

- ARCHINODE 어드민은 `admin/dashboard.html`(탭 4개: 브랜드·제품·아티클·검수관리, 1,121줄) + 상단바 링크로 흩어진 별도 페이지 5개(자문·투고·뉴스레터·디지털알림·아티클 카드형)로 돼 있다. 화면마다 로그인 검사·escapeHtml·토스트를 따로 갖고 있고, 무엇을 언제 누가 했는지 남지 않는다.
- 단번(THE BIDDING)은 관리자 화면 하나(16,127줄)에 사이드바 메뉴 6묶음·설정·공지·1:1 문의·검수 현황판·규정집을 넣어 "운영 콘솔"로 쓴다. 엑사(EX Works)는 알림·통합검색·임시저장을 전 화면 공통 장치로 갖는다.
- 제약: 서버 코드 없음(정적 HTML + Firebase compat + GitHub Pages), 규칙 게시는 `tools/deploy.ps1 -Rules`로 가능해짐, 어드민은 로그인 뒤라 배포 위험이 낮지만 **공개 페이지가 바뀌는 단계는 한울님 복귀 후로 분리**한다. 검수관리 탭(오픈 전 임시 도구)은 정식 기능과 얽지 않는다.

## 2. 선택지

### 2-1. 파일 구조 — 어디에 코드를 둘 것인가

| | 가. 단일 파일 확장 (단번 방식) | 나. 셸 + 화면 조각 js (추천) | 다. 지금처럼 별도 페이지를 늘림 |
|---|---|---|---|
| 방법 | `admin/dashboard.html` 하나에 사이드바와 모든 화면을 계속 넣는다 | `dashboard.html`은 **셸**(사이드바·인증·공통 부품)만 남기고, 화면 하나 = `admin/js/view-○○.js` 파일 하나. 모듈 없이 `<script src>`로 순서대로 싣는 전역 함수 방식 | 새 기능마다 `admin/leads.html`처럼 페이지를 하나씩 더 만든다 |
| 바뀌는 파일 | `dashboard.html`이 3~5천 줄로 커진다 | `dashboard.html` ±150줄(사이드바·script 태그), 새 파일 `admin/js/admin-core.js`·`admin-nav.js`·`view-*.js` 8~10개(각 150~400줄) | 페이지 8~10개 추가, 공통 코드 복사 반복 |
| 잃는 것 | Edit 도구 잘림 사고(사이트 2회 다운)가 난 "큰 파일 4종" 하나가 더 커진다. 매 수정이 줄 단위 Node 치환이어야 한다 | 전역 함수 이름 충돌 위험(파일별 접두어로 방어), 파일이 늘어 캐시 무효화(`?v=`) 관리, `lang.js`가 동적 내용을 안 훑는 문제는 그대로(이미 `rvSpan` 패턴으로 해결돼 있음) | 로그인 검사·escapeHtml·토스트가 페이지마다 복제됨(지금 5개 페이지가 이미 그렇다). 화면 간 이동이 전체 새로고침이라 통합 검색·알림 같은 공통 장치를 못 붙인다 |
| 규모 | 단계마다 큰 파일 수술 | 1단계에서 셸을 만드는 비용 3~4시간이 선투자 | 단계마다 가장 빠르지만 총량은 가장 큼 |

**추천: 나.** 이유 — 이 프로젝트에서 실제로 난 사고는 "큰 파일 통째 치환"이었다. 화면 하나가 파일 하나면 Edit 도구를 그대로 써도 안전한 크기(400줄 이하)로 유지된다. 단번이 단일 파일로 버틴 건 처음부터 줄 단위 치환 규율과 검수 인프라가 있었기 때문이고, 우리는 그 규율을 오늘 막 도입했다. 엑사도 실제로는 단일 파일(23,323줄)이라 "views-*.js 방식"이라는 이름은 정확하지 않다 — 여기서 제안하는 조각 방식은 어느 쪽의 복제도 아니고 **단번의 메뉴 구조 + 파일만 나눈 것**이다.
**추천이 잃는 것**: 화면 함수가 전역이라 `lead_`·`ntc_`·`set_` 같은 접두어 규율을 지켜야 한다. 그리고 기존 4개 탭 코드는 1단계에서 옮기지 않고 `dashboard.html`에 그대로 둔다(옮기는 건 빼기 작업이라 위험) — 그래서 한동안은 "셸 안에 옛 탭 코드가 남아 있는" 상태가 된다. 대가로 받아들일 만하다.

### 2-2. 메뉴 통합 — 별도 페이지 5개를 어떻게 할 것인가

| | 가. 전부 조각으로 흡수 | 나. 별도 페이지 유지 + 사이드바만 공유 (추천) |
|---|---|---|
| 방법 | consultations·trend-submissions·newsletter·notify·articles 5개(2,058줄)를 `view-*.js`로 다시 쓴다 | 5개 페이지에 `admin-nav.js` 한 줄을 넣어 **같은 사이드바**가 뜨게 한다. 메뉴 정의(`ADMIN_MENUS`)는 한 곳. 대시보드 안 화면은 `dashboard.html#leads`, 별도 페이지는 `consultations.html` — 사용자 눈에는 같은 메뉴 |
| 잃는 것 | 2,000줄을 다시 쓰는 동안 이미 잘 도는 상태 순환(자문 5단계·투고 5단계)을 깨뜨릴 수 있다 | 페이지를 오갈 때 전체 새로고침. 통합 검색이 그 5개 컬렉션은 별도 페이지로 "건너뛰기"만 해 준다(상세 모달을 못 연다) |
| 규모 | 8~12시간 | 1시간(1단계에 포함) |

**추천: 나.** 흡수는 "마지막에, 필요해지면" 선택 단계로 남긴다. 대가 없음에 가깝다(새로고침 한 번).

### 2-3. 정책 숫자 — 어디에 둘 것인가

| | 가. 코드에 그대로 | 나. `settings/config` 문서 하나 (추천) | 다. 카테고리까지 전부 설정으로 |
|---|---|---|---|
| 방법 | 지금처럼 for-brands.html·list-your-brand.html·brand-guide.html에 문구가 박혀 있음 | 요금 문구·무료 종료일·사이트 정보·연락 메일을 `settings/config`에 두고 어드민 「설정」에서 고친다. **값은 지금 코드 문구 그대로 옮기고 「안건 1 결정 대기」 표시**. 공개 페이지가 이 값을 읽게 하는 건 복귀 후 별도 단계 | 카테고리 10+69도 설정으로 |
| 잃는 것 | 규정집 "정책 숫자를 코드에 새로 박지 않는다"와 계속 어긋남 | 어드민에서 값을 고쳐도 공개 페이지는 복귀 후 단계까지 안 바뀐다(두 곳이 잠시 공존 — 화면에 "공개 페이지 연동 전" 표시) | 카테고리 페이지 79개가 정적 HTML이라 설정을 바꿔도 페이지가 안 생긴다 — 값만 옮기면 오히려 어긋남. 브랜드 포털 SUBCATEGORIES와 이중 관리 |
| 규모 | 0 | 2시간 | +3시간, 효과 없음 |

**추천: 나.** 카테고리는 코드에 둔다(이유: 카테고리 = 정적 페이지 79개와 1:1이라 설정으로 뺄 수 없다. 설정 화면에는 **읽기 전용으로 보여만** 준다). 어드민 이메일도 `firestore.rules`의 `isAdmin()`이 문자열로 갖고 있어 설정으로 못 뺀다(규칙이 문서를 읽게 하면 요청마다 읽기 1회 추가) — 설정 화면에 읽기 전용 표시만.
**추천이 잃는 것**: 안건 1이 결정될 때까지 설정 화면의 요금 칸은 "고칠 수 있지만 고치면 안 되는" 칸이다. 칸 옆에 빨간 표시로 막는다.

## 3. 단계별 순서 (되돌리기 쉬운 순 · 각 단계 = 한 번에 배포 가능한 단위)

공통 규칙:
- 각 단계는 **커밋 1개**. 롤백은 `git revert <해시>` 한 번(규칙을 넓힌 단계는 규칙도 되돌려 `-Rules` 재게시).
- 규칙이 바뀌는 단계는 **규칙 게시 → 화면 push** 순서. 규칙을 먼저 게시해도 화면이 없으면 아무 일도 안 생기므로 안전하다.
- 새 화면은 `escapeHtml` 전수, `data-en`/`data-ko` 짝(동적 내용은 기존 `rvSpan`/`rvAttr` 패턴을 `admin-core.js`로 올려 `t()`/`tAttr()`로 공용화), `confirm/prompt/alert` 신규 금지.
- 시간은 화이트 작업 시간 추정치. 블랙 검수는 별도(+30분/단계).

### 0단계 (사전, 코드 없음) — 규칙 게시 상태 맞추기
- 지금 `firestore.rules`의 `reviewIssues` 블록이 콘솔에 게시됐는지 기록이 없다. `492fc12`도 아직 push 전(origin보다 1 앞).
- 완료 조건: `tools/deploy.ps1 -Rules`로 현재 규칙이 게시되고, 검수관리 탭이 라이브에서 목록을 읽는다(브론즈 확인 — 어드민 비번 필요).

### 1단계 — 셸: 사이드바 + 공통 부품 + 대시보드 화면  ★ 규칙 변경 없음 · 공개 페이지 영향 없음
- **화면**: 왼쪽 사이드바(단번 NAV_GROUPS 축약 — 묶음: 대시보드 / 고객(리드·1:1 문의·전문가 회원) / 브랜드(브랜드·제품·아티클·브랜드 후보) / 접수(자문·투고·뉴스레터·디지털알림) / 운영(공지·활동 로그·검수관리·규정집·설정)). 아직 없는 화면은 숨김(`ADMIN_MENUS` 항목에 `ready:false`).
- **대시보드 화면**: 대기 건수 카드(브랜드 대기·제품·아티클·자문 pending·투고 pending·검수 검토대기) + 최근 활동 20건(2단계 전까지는 "활동 로그 준비 중").
- **파일**:
  - `admin/js/admin-core.js`(신규, ~150줄): `escapeHtml`·`t(en,ko)`·`tAttr`·`span`·모달 열기/닫기·토스트(`showToast` — 별도 페이지 5개에 이미 있는 것과 같은 모양)·`fmtDate`·`safeUrl`·`logAdmin()`(2단계 전엔 빈 함수)·`matchText()`(6단계용).
  - `admin/js/admin-nav.js`(신규, ~120줄): `ADMIN_MENUS` 배열 하나 + 사이드바 렌더 + `#hash` 라우팅(`dashboard.html#leads`) + 별도 페이지에선 현재 페이지 하이라이트.
  - `admin/js/view-dashboard.js`(신규, ~120줄).
  - `admin/admin.css`(신규, ~120줄): 사이드바·공통 스타일. 6개 페이지가 같은 파일을 읽는다.
  - `admin/dashboard.html`(**큰 파일, ±150줄**): 상단바 링크 6개 제거 → 사이드바 컨테이너, `.tabs` 4개는 사이드바 항목으로 매핑(기존 `.tab` 클릭 핸들러는 그대로 두고 사이드바가 그 탭을 "클릭"하는 식으로 연결 — 옛 코드 무변), `<script src="js/...">` 4줄. **기존 탭 코드는 옮기지 않는다.**
  - 별도 페이지 5개: `<div id="adminSidebar">` + `<script src="js/admin-core.js">`·`admin-nav.js` 각 3줄.
- **새 컬렉션·규칙**: 없음.
- **규모**: 3~4시간.
- **완료 조건**: 어드민 6개 페이지 어디서든 같은 사이드바가 보이고, 사이드바로 브랜드·제품·아티클·검수관리·자문·투고·뉴스레터·알림·아티클(카드형)에 다 갈 수 있으며, 브랜드 승인·검수관리 등록이 1단계 전과 똑같이 동작한다. 모바일(390px)에서 사이드바가 접힌다.
- **롤백**: revert 1건. 새 파일은 남아도 아무 페이지가 안 읽으면 무해.

### 2단계 — 활동 로그 + 브랜드 상태 이력  ★ 규칙 추가(어드민 전용) · 공개 영향 없음
- **화면**: 운영 > 「활동 로그」(`view-logs.js`, ~150줄): 시간·누가·무엇을(컬렉션·문서 이름)·어디서→어디로·메모. 필터: 기간(오늘/7일/30일)·종류. 대시보드 "최근 활동 20건"이 여기서 읽는다.
- **기존 코드 수정**(`dashboard.html` ~25줄): `updateBrand()`·`updateDoc()`·`saveReviewStatus()` 끝에 `logAdmin({...})` 한 줄씩. `updateBrand()`는 `history: arrayUnion({status, by, at, note: reason})`도 함께(검수대장 A-009 해결). 별도 페이지 5개의 `doAction()`에도 한 줄씩(각 파일 ~5줄).
- **새 컬렉션**: `adminLogs`(4-1절). `brands.history[]` 필드 추가(기존 `statusReason`·`statusChangedAt`·`statusChangedBy`는 그대로 둔다 — 공개 페이지·규칙이 참조).
- **규칙**: `adminLogs` — `allow create, read: if isAdmin(); allow update, delete: if false;` (덧붙이기만 되는 장부). `brands` 규칙은 어드민 update 조건이 status 4값만 검사하므로 `history` 추가에 규칙 변경 불필요.
- **규모**: 2~3시간.
- **완료 조건**: 브랜드를 정지→복구하면 활동 로그에 2줄, 브랜드 상세에 이력 2줄이 남고, 로그는 어드민이라도 지울 수 없다(콘솔에서 시도해 permission-denied 확인).
- **롤백**: revert + 규칙 되돌려 재게시. 이미 쌓인 `adminLogs` 문서는 남아도 무해.

### 3단계 — 설정 + 규정집 뷰어  ★ 규칙 추가(settings 공개 읽기 = 넓히기, PII 없음) · 공개 영향 없음
- **화면**:
  - 운영 > 「설정」(`view-settings.js`, ~250줄): 탭 3개 — ① 정책 값(요금 문구 EN/KO·무료 종료일·창립 요금 문구 — **각 칸 옆 「안건 1 결정 대기 — 규정집 2부」 빨간 표시, 저장은 되지만 공개 페이지 연동 전이라는 안내**) ② 사이트 정보(운영 주체·사업자번호·연락 메일·실비아 연락처·SNS) ③ 카테고리(읽기 전용 표 10+69, "코드 고정 — 정적 페이지와 1:1") + 어드민 이메일(읽기 전용, "규칙 파일 고정").
  - 운영 > 「규정집」(`view-regulations.js`, ~120줄): `../docs/ARCHINODE 규정집.md`·`작업일지.md`·`검수대장.md`를 fetch해 렌더. **`docs/`가 GitHub Pages에 공개 서빙되는 것을 확인했다(HTTP 200)** — 그래서 fetch는 된다. 마크다운 → HTML은 cdnjs `marked` + `DOMPurify`. 파일 목록은 코드에 3개 고정(디렉터리 목록은 정적 호스팅에서 못 얻음).
- **새 컬렉션**: `settings/config` 1문서(4-2절). 초기값은 화면의 「기본값 채우기」 버튼이 코드에 박힌 현재 문구로 만든다(단번 `settings/config` 기본값 패턴 축약).

## 4. 데이터 계약

공통 규약:
- **history 패턴은 `reviewIssues`와 같다**: `history: [{ status, by, at(ISO 문자열), note }]`, 상태가 바뀔 때마다 `arrayUnion`. 등록 시 첫 줄 `{status: 초기값, by, note: '등록'}`.
- `createdAt`·`updatedAt`은 `serverTimestamp()`. `by`는 로그인 이메일(어드민) 또는 uid(브랜드) — 어느 쪽인지 `byRole`로 구분.
- 테스트 데이터는 이름 앞에 `[테스트-○○]`.
- 상태값은 영어 소문자 고정(공개 페이지·메일 문구에 섞이므로). 화면 라벨만 `data-en/data-ko`. (검수관리의 한글 상태값은 임시 도구라 예외 — 손대지 않는다.)

### 4-1. `adminLogs` (2단계, 어드민 전용, 덧붙이기만)
```

by          어드민 이메일
action      'brand.status' | 'product.status' | 'article.status' | 'review.status' | 'lead.status' | 'lead.assign'
            | 'inquiry.answer' | 'notice.save' | 'settings.save' | 'prospect.status' | 'prospect.import'
target      { col: 'brands', id: docId, label: 'Fritz Hansen' }   ← label은 사람이 읽는 이름
from        이전 값 (문자열, 없으면 '')
```

### 4-3. `leads` (4단계) — 규칙 파일에 "선언만" 있던 컬렉션을 활성
```

history     [{status, by, byRole:'admin'|'brand', at, note}]
```
질의: 어드민 `orderBy('createdAt','desc')` / 포털 `where('brandId','==',uid)` **orderBy 없이**(클라이언트 정렬 — `brandId+createdAt` 복합 색인을 피한다).

### 4-4. `notices` (5단계)
```
title_en, title_ko, body_en, body_ko   (본문은 줄바꿈만, HTML 아님 — 표시 시 escapeHtml + <br>)
audience   'brand' | 'site' | 'all'
visible    true/false     pinned   true/false     order  숫자
createdAt, createdBy, updatedAt, updatedBy
```
포털은 `where('visible','==',true)`만 걸고 audience 필터는 클라이언트(복합 색인 회피, 문서 수가 적음).

### 4-5. `inquiries` (5단계)
```
fromUid, fromRole('brand'|'professional'), fromEmail, fromName(브랜드명 또는 표시 이름)
subject, body
status     'open' | 'answered'
answer, answeredAt, answeredBy
createdAt, updatedAt
history    [{status, by, at, note}]
```

### 4-6. `prospects` (7단계, 어드민 전용)
```
brandName, country, category, website, contactName, contactEmail
status     'new' | 'contacted' | 'replied' | 'interested' | 'declined' | 'bounced' | 'applied'
firstContactAt, lastContactAt (문자열 'YYYY-MM-DD' — 실비아 표와 같은 형식)
template   'A' | 'B' | 'C' | ''       response  응답 요약 한 줄
bounced    true/false                  owner     'silvia'
note, batch('b1'|'b2'), linkedBrandId(입점 신청과 매칭되면 brands 문서 id)
createdAt, updatedAt, history[]
```

### 4-7. 기존 컬렉션에 더하는 필드
- `brands.history[]`(2단계) · `brands.refSource`(7b) — 둘 다 없어도 화면이 도는 선택 필드.
- `users`: 변경 없음(6단계는 읽기만).

## 6. 리스크

1. **큰 파일**: `admin/dashboard.html` 1단계 ±150줄·2단계 ±25줄, `brand-portal/dashboard.html` 4a +120·5 +100줄. 전부 줄 단위 Node 삽입, 끝나면 `</html>`·줄 수 확인. 1단계에서 옛 탭 코드를 "옮기지 않는" 이유가 이것이다.
2. **규칙 순서·게시 순서**: 새 블록을 기본 차단 아래에 넣으면 무효. 규칙 게시 전에 화면을 push하면 "권한 오류"가 사용자에게 보인다 — 검수관리 탭처럼 화면이 "규칙 게시 확인" 안내를 띄우게 한다.
3. **다국어**: `lang.js`는 로드 때 한 번 훑는다. 동적으로 그린 화면은 `t()`/`tAttr()`로 현재 언어 텍스트 + 속성 짝을 같이 찍어야 한다(검수관리 탭 패턴). 어드민은 영어 우선이지만 규정 "이중 언어 필수"라 라벨 전부 짝.
4. **XSS**: 새 화면 8개 전부 `${}` 출력에 `escapeHtml`. 특히 ① `onclick="fn('${id}')"` 문자열 주입 대신 `data-id` + 이벤트 위임 ② 규정집 뷰어는 `DOMPurify` 필수(md가 리포 안 파일이어도 원칙) ③ 리드·문의 본문은 외부 입력(4b 이후 방문자가 쓴다) — 저장 시 이스케이프가 아니라 **표시 시 이스케이프**로 통일(list-your-brand.html은 저장 시 이스케이프라 두 방식이 섞인다 — 검수대장 A-003과 같은 계열, 복귀 후 정리 항목). 엑사에서 한 곳이 60곳으로 번진 사례를 기억할 것.
5. **전역 이름 충돌**: 파일별 접두어(`lead_`·`ntc_`·`inq_`·`set_`·`usr_`·`pros_`·`log_`). `admin-core.js`가 정의한 이름(`escapeHtml`·`t`·`showToast`·`openModal`)을 별도 페이지 5개가 이미 각자 갖고 있다 — 1단계에서 core를 싣되 **`function` 선언은 뒤에 오는 것이 이긴다**(같은 동작이라 무해). 단 `const`·`let` 재선언은 문법 오류로 페이지가 죽는다 — 블랙이 중복 선언을 반드시 본다.
6. **캐시**: GitHub Pages는 js를 오래 캐시한다. `<script src="js/view-leads.js?v=20260912">` 형식으로 배포마다 버전 문자열을 올린다(lang.js가 이미 이 방식).
7. **읽기량**: 대시보드가 열릴 때 브랜드·제품·아티클·리드·회원·로그를 전부 읽는다. 지금 문서 수가 적어 무료 한도 안이지만, 각 화면은 `limit(200)`을 기본으로 하고 "더 보기"를 둔다. 통합 검색은 이 캐시만 뒤진다(추가 읽기 없음).
8. **복합 색인**: 포털 리드 조회·공지 조회는 `where` 하나 + 클라이언트 정렬로 색인을 피했다. 화이트가 `orderBy`를 덧붙이면 콘솔에서 색인을 만들어야 동작한다 — 지시서에 명시.
9. **`docs/`·`sales/` 공개 서빙**: 규정집 뷰어가 fetch할 수 있다는 건 **누구나 받을 수 있다**는 뜻이다. `sales/cold-email-templates.md`·`brand-prospects-*.xlsx`(후보 브랜드 담당자 정보 추정)도 라이브 URL로 열린다(HTTP 200 확인). 이 설계는 그 상태를 바꾸지 않지만, **한울님 결정 사항**으로 올린다: `sales/`를 리포 밖(archi-diary처럼 .gitignore)으로 옮기고 7a에서 Firestore로 가져오면 공개 노출이 끝난다. `docs/`는 규정집이 사업 판단(요금 미결 등)을 담고 있어 공개가 적절한지 판단 필요 — 비공개로 가면 규정집 뷰어는 Firestore `settings/regulations`(어드민이 md 본문을 붙여넣기)로 바꿔야 한다(+1시간).
10. **검수관리 탭과의 경계**: 활동 로그가 검수관리 상태 변경도 기록하지만(`review.status`), 검수관리 데이터·규칙은 손대지 않는다. 오픈 후 검수관리를 걷어낼 때 `ADMIN_MENUS` 한 줄과 dashboard 안의 해당 코드만 지우면 된다.
11. **브랜드 포털의 `alert()`**: 기존 코드에 남아 있다. 새로 넣는 Inbox·Support 탭은 확인창 없이. 기존 것은 손대지 않는다.

## 7. 확인 못 한 것

- **Firestore 실데이터**를 못 봤다(어드민 비번 없음). 브랜드·제품·회원 수, `leads`에 문서가 있는지(규칙만 있고 "미사용"으로 적혀 있으나 실제 0건인지), 라이브 어드민이 지금 정상 동작하는지 — 전부 추정.
- **규칙 게시 상태**: `reviewIssues` 블록·`mail` 블록이 콘솔에 게시됐는지 기록 없음(작업일지 A-④). 0단계에서 맞춘다.
- **Trigger Email Extension 설치 여부**(작업일지 A-③). 미설치면 4a·5의 메일은 `mail` 문서만 쌓이고 발송되지 않는다 — 화면 동작에는 영향 없음.
- **`sales/brand-prospects-2026-06-v2.xlsx` 열 구조**: 파일을 열지 않았다(실비아 지침의 J~L열 설명으로 추정). 7a의 CSV 열 매핑 미리보기가 이 불확실성을 흡수한다.
- **어드민 6개 페이지의 모바일 동작**: 사이드바를 접는 CSS는 설계했지만 실기기 확인은 브론즈.
- **단번 활동 로그 원형**: 단번의 `opsLogs`는 서버 함수 실행 로그라 어드민 활동 로그가 아니다. 4-1은 엑사 `logActivity`의 축약이며 단번에서 가져온 것이 아니다.
- **`marked`·`DOMPurify`가 GitHub Pages 어드민 페이지에서 로드되는지**: 이 사이트에는 CSP 헤더가 없어(Cloudflare 보안 헤더는 이연 P1-6) 될 것으로 추정. 3단계 블랙이 로컬에서 확인.
- **한울님 부재 기간**과 복귀 후 4b·7b·사이트 공지를 언제 붙일지 — 이 문서는 순서만 정하고 날짜는 안 정했다.
